# 面向用户的文档写作原则

本原则适用于项目 README、Release 正文及其他面向用户的说明。编写或修改这些文档前，先明确用户需要知道什么，再选择必要的细节。

## README：产品做了什么，用户怎么用

- 介绍产品能力、主要变化，以及安装、首次使用和常用操作。
- 用用户熟悉的功能和界面名称表达，保持完成操作所需的粒度。
- 不让内部实现、维护流程或细粒度技术说明挤占用户的阅读路径。现有项目 README 可作为粒度参考。

## Release：这次更新了什么

- 只说明本次新增、修复或改善的功能与体验，让用户看懂更新对自己的影响。
- 直接写变化与结果，例如“修复立直后摸打建议不显示的问题”。
- 不写测试清单、验证范围、实局统计、日志证据、内部实现、发布流程或技术边界论证。
- 不重复介绍未变化的功能，也不反复附加下载、安全或兼容性说明；下载与安装最多保留 README 链接。
- 只有用户确实需要操作或理解关键行为时，才补充简短提示，例如“恢复后的建议需手动操作”。不要将提示展开为协议条件或实现说明。

## 内容取舍与准确性

- 逐句判断：这句话能否帮助用户理解功能变化、完成操作或作出使用决定？不能就删除，或放入对应开发文档。
- 验证、调试、构建和维护信息写入开发文档，不把发布说明写成工程验收报告。省略验证过程不代表降低实际验证要求。
- 简洁不能改变事实：保留会影响实际使用的操作要求和行为条件，不夸大功能或承诺尚未支持的行为。
- 中英文说明保持相同的内容与粒度，不在某一语言中额外加入技术解释。

## 改写示例

| 负面案例 | 改写方式 |
|---|---|
| 0.1.3 的“验证范围与日志读取”：实局统计、点击／请求／服务器证据链、审计脚本用法。 | 删除该章节，在更新条目中写“修复立直后摸打建议不显示，以及荣和、自摸被跳过的问题”。 |
| 0.1.1 的“边界与下载”中的边界说明：输入请求与成功的区别、反馈超时、协议归属辨识、Lua 与重试策略。 | 删除边界论证，在更新条目中写“新增自动操作记录，可查看倒计时、执行过程和结果；未确认操作以红色显示”。 |

提交前检查：README 是否说明了产品与用法，Release 是否说明了本次变化，是否混入了用户不需要的验证或实现细节，中英文是否一致。
